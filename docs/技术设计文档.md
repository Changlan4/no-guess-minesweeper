## 一、项目概述

一款 Windows 平台的扫雷游戏，核心卖点是**每一局都经过求解器验证，保证可以纯逻辑推理通关，不需要盲猜**。

### 功能清单（均已实现）

| 功能 | 说明 |
|---|---|
| 无猜雷盘 | 首击后生成，并由求解器验证全盘可纯逻辑推理完成 |
| 首击安全 | 首次点击的格子及其 8 邻居永远不是雷 |
| 三档难度 | 初级 9×9 / 10 雷、中级 16×16 / 40 雷、高级 16×30 / 99 雷，菜单随时切换 |
| 快速排雷 | 左右键同时按已翻开的数字格：旗数够就掀开周围，不够则闪烁提示 |
| 主题 | 4 套暗色配色（午夜薄荷 / 午夜樱粉 / 午夜紫罗兰 / 午夜海蓝），适合长时间使用 |
| 交互反馈 | 悬停高亮、按下凹陷、揭格展开动画（连片展开按距离扩散）、插旗脉冲 |
| 键盘操作 | 方向键移动光标、空格/回车掀开、`F` 插旗、`F2` 重开、`H` 提示 |
| 提示 | 从**已翻开区域的边界**上随机给出一个逻辑上必然安全的格子并高亮 |
| 失败复盘 | 踩中的那颗雷用 💥 标出，插错的旗用 ❌ 标出 |
| 排行榜 | 每种难度保存最快的前 10 次成绩 |
| 统计 | 总局数、胜负、胜率、获胜平均用时、当前连胜、最长连胜 |
| 窗口状态 | 尺寸与最大化状态持久保存 |

## 三、核心算法

### 3.1 布雷与首击安全（`GameBoard.PlaceMines`）

首击之后才布雷，安全区 = 首击格及其 8 邻居（共 9 格，边界处更少）。

雷位用**部分 Fisher-Yates 洗牌**从候选格中抽取：线性时间、分布均匀，并且在雷数超过可用格数时会明确抛出异常，而不是像早期版本那样用「随机撒点撞了就重试」的拒绝采样无限循环。

### 3.2 无猜求解器（`SolverService`）

判定「当前局面能否纯逻辑推到通关」，推理分两层：

**第一层 · 基础计数**
遍历每个已翻开的数字格，统计周围未翻开格与已插旗数：
- 剩余雷数为 0 → 周围未翻开格全是安全格
- 未翻开格数恰好等于剩余雷数 → 全是雷

**第二层 · 约束图连通分量分解 + 分量内完整枚举**
第一层推不动时，把每个数字格视为一条约束方程「这组未知格中恰有 k 个雷」，然后：

1. 按「是否共享同一条约束」把未知格划分成互不相干的连通分量；
2. 对每个分量**完整枚举**全部合法赋值（带约束剪枝，单分量上限 40 个变量、50 万搜索节点）；
3. 只采用**在该分量所有合法解中都成立**的结论：某格在所有解里都是雷 → 必然是雷；都是安全 → 必然安全。

> **为什么按分量独立统计是安全的**：真实雷分布必然是「每个分量各取一个合法赋值」的组合，
> 所以某格若在某个分量的所有合法赋值中都是雷，它在真实盘面里也必然如此。
> 该结论无须全局约束即可成立，因此求解器**绝不会推出错误答案**，最坏情况只是「推不动」。

**正确性保障措施**
- 推出「安全格」或「雷格」时用真实雷分布做自检，一旦不符立即放弃（返回 `Contradiction`）；
- 盘面上存在与真实雷分布不符的旗（玩家插错旗）时，直接拒绝分析——因为整个推理建立在「旗都是对的」这一前提上；
- 因此 `Analyze` 的契约是：**要么给出的结论必然正确，要么明确报告无法判断**。

**生成流程（`Generate`）**
最多尝试 200 次，每次随机布雷后用上述求解器验证；返回 `GenerationResult`，其中
`GuaranteedNoGuess` 明确告知是否验证通过。**不再像早期版本那样在验证失败时静默交付一个需要猜的盘面。**

### 3.3 快速排雷（`GameBoard.Chord`）

对已翻开的数字格：
- 周围旗数 == 数字 → 掀开其余未翻开格（可能踩雷，踩雷即失败）
- 周围旗数 < 数字 → 返回「闪烁提示」列表，提醒玩家旗不够
- 旗数 > 数字 → 不操作

注意：本作**不会自动插旗**（v1.0 文档曾声称会自动标旗，实际从未如此）。

## 四、性能与渲染设计

### 4.1 绘制（`BoardCanvas.OnRender`）

棋盘用 `Canvas` + `OnRender` 一次性自绘 480 个格子，关键是**不再每帧重建绘制对象**：

| 优化 | 原因 |
|---|---|
| `Pen` 静态缓存 + `Freeze()` | 未冻结的 Freezable 会让 WPF 无法复用渲染指令；原实现每帧 new 出上千个 Pen |
| `FormattedText` 按 (文本, 量化字号, 颜色, DPI) 缓存 | 它构造时要走字体回退与字形布局，很贵；原实现每帧重建上百个 |
| 集合变化通知合并 | 重建棋盘会连续触发几百次 `CollectionChanged`，合并成一次重绘 |
| 动画定时器按需启停 | 没有动画时完全不产生重绘 |

**渲染成本基准**（Release / .NET 9，30×16 共 480 格、格子 30px，由 `RenderBenchmarkTests` 实测）

| 项目 | 成本 |
|---|---|
| 全盘重绘一帧（含软件光栅化到 900×580 位图） | ≈ 10.0 ms（60fps 预算的 60%） |
| 视觉树未变化时的重绘 | ≈ 10.5 ms |
| **纯绘制指令录制（不含光栅化）** | **0.60 ms（仅占 6%）** |
| 旧实现每帧的额外分配开销（480 个 FormattedText + 960 个 Pen） | ≈ 1.08 ms（已消除） |

**为什么没有引入 `DrawingVisual` 脏格分层重绘**

绘制指令录制只占全盘重绘的 6%，瓶颈在光栅化；而上述测量走的是 `RenderTargetBitmap`
软件光栅化，本来就是真实上屏渲染的成本**上界**（本机实测 WPF 渲染层级 `Tier=2`，即硬件加速）。
按脏格分层能省下的只是那 6% 里的一部分，收益远小于它带来的架构复杂度，因此不做。

作为补偿性的保险，`BoardCanvas` 会读取 `RenderCapability.Tier`：**软件渲染环境下自动不播动画**
（远程桌面、虚拟机、显卡驱动异常等），优先保证点击跟手。

### 4.2 动画

- 16ms 驱动，进度每帧 +0.17，约 6 帧（≈100ms）走完；
- 揭格用 `EaseOutCubic` 从 0.84 倍缩放弹到 1.0；
- 插旗用正弦脉冲 1.0 → 1.22 → 回弹；
- 轻触反馈（Pulse）不用缩放，改成一次白色高亮按 `0.45 × (1 - progress)` 单调淡出，与揭格区分开；
- **连片展开按到落点的切比雪夫距离错峰**（最多 8 帧），形成从点击处扩散出去的观感；
- 动画目标由 `MainViewModel` 放入待播队列，`BoardCanvas` 在重绘前消费。

### 4.3 生成与响应

- 首次点击后在后台线程生成雷盘，UI 不阻塞；
- 生成期间 `IsBusy` 互斥，重复点击不会再起第二个任务（原实现会，导致两次生成的棋盘互相覆盖、玩家点击"没反应"）；
- 支持取消：重开或关窗会取消在途任务；
- 计时用 `Stopwatch`，不受系统时间调整影响。

## 六、配置与数据存储

位置：`%AppData%\Minesweeper\`

**settings.json**
```json
{ "winW": "900", "winH": "580", "winState": "0", "theme": "MintNoir" }
```

**records.json**（v1.2 起存排行榜与统计；读取时会自动迁移 v1.1 及更早的旧格式）

```json
{
  "高级": {
    "TopTimes": [ { "BestTimeSeconds": 146.7, "Date": "2026-08-24T13:48:41+08:00" } ],
    "GamesPlayed": 12,
    "GamesWon": 5,
    "CurrentStreak": 2,
    "BestStreak": 3,
    "TotalWinSeconds": 823.4
  }
}
```

旧格式（每个难度直接是一条 `{ BestTimeSeconds, Date }`）在读取时会被迁移进 `TopTimes`，
迁移后那两个兼容字段仍然每次写回文件，旧版本读同一份文件时依然能看到最佳成绩。

> ⚠ **窗口尺寸必须校验**：窗口在最大化状态下关闭时 `Window.RestoreBounds` 可能是 `Rect.Empty`，
> 而 `Rect.Empty.Width` 恰好是 `double.NegativeInfinity`。它会被格式化成 `"-∞"` 存进配置，
> 下次启动赋给 `Window.Width` 直接抛异常——**游戏再也打不开**。
> 现在读写两端都会拒绝 NaN / 无穷 / 越界值（`ScoreService.IsUsableWindowSize`）。

## 九、已知限制与后续方向

- 求解器**不做跨分量的全局雷数推理**（例如「两个分量合起来恰好用完全部雷数」这类推断）。
  这是刻意取舍：不做只会少推一些、绝不会推错。若将来要提升完备性，可在此加一层分量间 DP。
- 单分量变量数超过 40 或搜索超预算时，该分量本轮不参与推理（不影响其他分量）。
- UI 层只有「构造 + 渲染」的冒烟测试，没有自动化交互测试。
- 可扩展方向：撤销、重开同盘、3BV/效率与 CPS 统计、自定义难度、深色主题、音效、种子分享。

## 十、修订记录

---

**v1.6**（按第五轮实测反馈）
- **修复快速排雷的黄色闪烁闪了两下**：`OnFlashTick` 里算出来的 `on` 从未参与判断，
  实际执行的是无条件的 `IsFlashing` 取反，于是每个 Tick 翻转一次、共形成两个亮起周期。
  现在第一次 Tick 就收尾，并把亮起时长从 200ms 放宽到 260ms（只闪一次，要看得清）
- **修复重复按 H 只有第一次显示**：`FlashHint` 用 `Storyboard.Remove` 清理上一轮动画，
  而 `Remove` 会让该 storyboard 的 `Completed` 在下一次 `Begin` 启动新动画的那一刻**再触发一次**；
  那次迟到的回调把刚设好的 `HintCell` 清成 `(-1,-1)`，于是动画照跑、画面全无。
  现在改用 `Stop` 清理，并给 `Completed` 加「身份守卫」（不是当前这一轮就不许动共享状态）
- **修复胜利后状态栏的剩余雷数永远不归零**：胜利收尾直接改 `Cell.State`，绕过了唯一维护
  `FlaggedCount` 的 `ToggleFlag`。新增 `GameBoard.SyncFlaggedCount()` 在收尾后重算，
  并补一次 `UpdateStatus()`
- 剩余雷数不再钳到 0：旗插多了显示负数（经典扫雷的做法），并用警示色标出来
- `ClearHint()` 改为走「一次性请求」通知通道，画布上的提示高亮会立刻撤掉，
  不再出现「玩家已经继续操作、旧高亮还闪完 430ms」的残影；顺带让
  `MainWindow` 里那条 `Board.ClearHint()` 分支从不可达变成可达
- `BeginGenerateBoard` 的异常安全：`IsBusy` 置位与通知移入 `try`（此前订阅者一旦抛异常，
  `finally` 不执行，`IsBusy` 永久为 true、整个棋盘失去响应）；`CancellationTokenSource.Token`
  提前取出，避免玩家重开时 `Dispose` 之后访问抛 `ObjectDisposedException`；
  并处理「首击直接通关」（`GameOver` 的盘面现在会立刻走胜负收尾）
- 难度切换后键盘光标会越界：`EnsureCursor` 原来一进来就 `if (_cursorVisible) return`，
  小棋盘上旧坐标再也得不到修正，表现为光标消失、空格/F 没反应。现在每次都钳位
- 尚未开局就按 H 不再报「无法只靠逻辑确定」，改为提示先点开一格
- 踩雷/胜利时停掉闪烁定时器；`NewGame` 与每次操作前清空待播动画队列，避免残留动画迟到播放
- `HitTestCell` 先挡负坐标：`(int)` 对负数是向零取整，棋盘左上外侧原本会被当成 `(0,0)`，
  把棋子拖出左上角再松手会误掀那一格
- 和弦路径补上 `CaptureMouse()`：两键按住拖出棋盘外松手时，`_chordActive` 不再残留
  （残留会把之后的第一次点击吃掉）
- `ScoreService`：改为「写临时文件再整体替换」的原子写，读取失败不再全量清空，
  损坏的 `records.json` 会留一份 `.corrupt` 副本；`settings.json` 的路径也可注入，
  测试不再写玩家真实配置（此前跑一次单元测试就会把玩家的窗口尺寸/最大化状态覆盖掉）
- 中途弃局单独计数（统计窗口新增「中途重开」一行），不再被当成失败拉低胜率
- 新纪录的判定与存储统一用同一位小数：此前 10.04 存成 10.0、下次 9.98 会弹「新纪录」，
  但榜单上新旧两条都显示 10.0 秒
- 主题资源加载失败时不再改 `ThemeService.Current`（此前会与实际生效的配色长期不一致）；
  主题菜单在认不出名字时提前返回，不再出现「勾选变了但配色没变」

**v1.5**（按第四轮实测反馈）
- **修复主题从未真正嵌入程序集的问题**：csproj 里把 `Themes/*.xaml` 声明成了 `Content`，
  这会挡掉 WPF SDK 的默认 `Page` 处理，主题只被复制到输出目录、不编译成 BAML。
  于是程序只能靠「exe 旁边必须有 Themes 文件夹」才能跑（单独拷 exe 就掉配色）。
  现在移除该声明，主题以 BAML 嵌入，发布产物不再需要 Themes 目录
- 主题引用统一改为 pack URI（`/Minesweeper;component/...`）；相对 URI 是按入口程序集解析的，
  换宿主进程就会找不到资源
- **修复深色界面下菜单文字看不清**：`MenuItem` 之前的样式写在 `Menu.Resources` 里未生效，
  改为在 `App.xaml` 定义应用级样式，并对每个菜单项显式绑定前景/背景色
- 系统标题栏切深色（`DwmSetWindowAttribute`），消除「浅色标题栏 + 深色主体」的割裂
- 表情按钮加中亮度药丸底：emoji 直接在深色状态栏上几乎不可见
- **快速排雷时被点的那一格现在也会脉冲一下**：之前只有周围被掀开的格子有动画，
  被点的数字格毫无反应（而单独右键点它却有回弹），看起来像「和弦没有动画」
- 旗数不匹配时的闪烁从 1 次改为 2 次，状态栏明确写出「周围几面旗 / 数字是几」
